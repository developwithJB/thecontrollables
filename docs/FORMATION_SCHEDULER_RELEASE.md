# Formation reminder scheduler repair

## Problem and change
The two existing hourly cron jobs present an anon JWT, while send-daily-nudge requires service-role or admin authentication. They both invoke the same morning-selection function. The verified sender remains `The Dashboard <noreply@thedashboard.agbcoaching.com>`; no new sender, domain, recipient import or billing change is needed.

A dedicated 256-bit scheduler token authorizes only a normal scheduled run or a non-sending health probe. It cannot authorize targeted sends, test mode, forceSend or arbitrary body fields. Existing service-role/admin behavior and gateway JWT verification remain intact. The installation script reads the existing public anon bearer and endpoint from the morning job, references the dedicated token through encrypted Vault storage, and replaces the duplicate runners with one hourly job at five minutes past the hour. Existing timezone, consent, suppression and reviewed-content selection rules still decide who can receive a message.

## Credential approval and installation
This change is reviewable before any production credential exists. Installing it creates a new persistent access credential, so the browser safety policy requires action-time user confirmation. No production secret is included in this PR or generated by tests.

After approval, generate a fresh 32-byte cryptographically random token securely through project tooling. Store the same lowercase 64-character hex value as the edge secret `FORMATION_SCHEDULER_TOKEN` and Vault secret `formation_scheduler_token`. Never display, log, commit or paste the value into browser chat. This token is scoped to the scheduler; do not copy the service-role key into Vault.

Deploy only `send-daily-nudge` and its exact committed imports, preserving existing verify_jwt=true. Before scheduling, call its new `{"schedulerHealthCheck":true}` probe with the existing valid anon bearer plus the dedicated header. It must return `schedulerAuthenticated:true` without an audience query, email send or provider call. Invalid credentials and force/targeted payloads must still be rejected. Then execute `scripts/ops/configure-formation-scheduler.sql` atomically in the intended project. It refuses to alter jobs unless the expected Vault secret and existing anon configuration exist. Read back only job count, schedule and presence of a Vault reference; never the secret or raw headers.

Retain the existing sender. No immediate real email is required by the health probe. Keep `formation_email_verified=false` until delivery validation is sufficient; a credential probe alone is not a delivery receipt. Strict 75-day content approval remains separate and gated.

## Tests and rollback
The unit contract rejects missing/incorrect credentials and every targeted/override payload. The local PostgreSQL fixture runs the exact installation DO statement against a disposable cron schema and synthetic Vault secret, proving a single scheduled job, a Vault reference instead of a plaintext credential, and the expected body. All fixtures roll back. Deno checks the full endpoint. Run no production sends as part of automated tests.

For rollback, disable the new morning job first, restore the previous committed endpoint, and rotate or retire the dedicated token through secure tooling. Do not re-enable the old broken duplicate anon jobs or weaken endpoint authentication.
