# First 100 paying customers: launch funnel

Baseline: `main` at `fccd94a` (October 21, 2026). This document describes the implementation branch and release acceptance; it is not evidence that the branch is published or that production telemetry or payments passed.

## Goal and scope

Remove friction between a campaign visit, a first meaningful saved practice, returning in week one, and choosing optional paid support. Scope: campaign entry, privacy-safe funnel events, the named Instagram link, eight-character new/reset passwords, and contextual Pro offers. Preserve free Read Along, independent content review, server-owned AI limits, billing, and private data.

The 2-4% free-to-paid rate is a planning assumption, not observed Dashboard performance. At that assumed rate, 100 paid customers requires 2,500-5,000 free signups. Visits are a separate denominator. A year-long simulation cannot establish this conversion rate.

## Funnel events and their actual meaning

Growth events always use `ingest-telemetry`; PostHog mirrors them only when configured. Sentry is error monitoring, not a prerequisite for the growth sink. Do not describe network acceptance as proof an event was queried in its destination.

| Stage | Event / authoritative source | Meaning and caveat |
| --- | --- | --- |
| Visit | `landing_view` | One per browser session, including the bio route. Not a unique person or proof of intent. |
| Signup request accepted | `signup_submitted` | Successful Auth signup response. May still require email confirmation; not verified activation. |
| Authenticated entry | `authenticated_visit` | Once per account per browser session through Auth; allows the sink to derive the owner and associate the session. Not necessarily a newly created account. |
| First meaningful practice | `first_circuit_completed` | Emitted only after a successful save that satisfies a circuit. Browser dedupe is best-effort; authoritative first-practice counts come from saved formation rows. |
| Day-seven return | `day7_return` | Today loaded on the sixth local calendar date after signup (signup day is day 1), using the device's local timezone. Not seven completed practices or strict-day credit. |
| Offer | `pro_offer_viewed`, `pro_offer_clicked`, `pro_offer_dismissed` | Only fixed placements, no reflection or chat text. A view means mounted in the rendered UI; not an eye-tracking or viewport guarantee. |
| Checkout | `checkout_requested`, `checkout_opened`, `checkout_failed` | Request initiated, checkout URL returned/navigation attempted, or request failed. None is a completed payment. |
| Paid | Signed Stripe event plus server billing record | A browser return URL is never payment authority. Use signed webhook processing and the resulting subscription/entitlement, deduplicated by Stripe event/subscription. |

The sink derives user identity from the authenticated request, ignoring client identity. Anonymous events have a session ID, not an authenticated user. Same-browser sessions can connect stages; another device, cleared storage, blockers, network failures, or the existing 30-events/session ceiling can create gaps. Do not label raw stage counts as a complete cohort conversion rate. Production joins must preserve privacy and define signup cohort, conversion window, and unique subscription semantics.

## Release order and production acceptance

1. Review and deploy the updated `ingest-telemetry` allowlist before publishing the frontend. No schema migration is required.
2. Configure **hosted Supabase Auth** minimum password length to 8 and verify server rejection of a seven-character new/reset password. The local `supabase/config.toml` setting does not update hosted Auth. Existing six-character passwords must still sign in. See [Supabase password security](https://supabase.com/docs/guides/auth/password-security).
3. Publish the reviewed frontend through Lovable. Test `/start` on mobile and desktop; complete signup and first practice with a designated test account.
4. Query stored events for that tagged test session. Confirm visit, signup, authenticated entry, first saved practice, offer, and checkout request events arrive. Use the aggregate read-only `scripts/sql/verify-launch-funnel.sql` as an arrival check, not a cohort conversion calculation. Verify day-seven return using an appropriate real cohort; a local clock test does not prove production retention.
5. Select the actual Dashboard PostHog organization/project and configure its public project token in Lovable. Check event arrival there. The connected PostHog account currently has no clearly identified Dashboard project; do not query another product's data or silently install its token.
6. Verify Sentry configuration and an approved synthetic handled error separately. Do not put account details or private context in the probe.
7. Run one explicitly approved production purchase at the displayed plan/amount; verify payment, signed webhook, account access, and subscription management. Sandbox results do not satisfy this item. No live charge is made by this PR.
8. Verify confirmation and password reset delivery on controlled Gmail, iCloud, and Outlook inboxes. Check the link, destination, expiry and reset completion. Do not use customer inboxes as fixtures.
